The concurrency option

'parallel'
The default, shown above: a second call runs at once, in parallel.
'queue'
A second call waits for the previous one to settle, then runs: the server receives the writes in call order. Use case: move an item to the top.
'queue-latest'
Waits like 'queue', with one waiting call at most: a newer call replaces it, and the replaced call's mutate() rejects at once with an AbortError ('Replaced'), never sent, no callback. Only for writes carrying the whole state. Use case: autosave.
'drop'
While a call is in flight, mutate() rejects at once with an AbortError ('Dropped'): mutationFn isn't called, no callback runs, the signals don't change. Use case: pay.
mutationQueue()
One call at a time, in call order, across every mutation given the same queue. Use case: rename, then delete.
{{ '{' }} queue, key {{ '}' }}
The same, per key: a call waits for the previous call with the same key, other keys run at once. A call given the queue without a key waits for every key, and the calls after it wait for it. Use case: save per document.

In every mode, the state signals follow the mutation's latest call, and pendingInputs() lists the queued calls too. A call that never left ('Dropped', 'Replaced', or a reset() while queued) makes wasNeverSent(error) true: see cancellation.
